# ingine on an RTX 3090 (sm_86)

Upstream: `upstream` remote = github.com/satellitedown/inkling-2-mini-abliterated-ingine (bf372d0).
Local branch: `rtx3090`. The RTX 5090 (`sm_120a`) build should behave as before: the
replacements sit behind `INGINE_AMPERE`, which CMake defines only for `CMAKE_CUDA_ARCHITECTURES=86`. The one
shared change is that the FP8 readers in gemv / dense / prefill / attention now go through
`kernels/common/fp8.cuh`, which on sm_120a emits the same `cvt.rn.f16x2.e4m3x2` that `cuda_fp8.h` did.

## Build

```bash
cd native
T=$PWD/../.cuda-toolkit/nvidia/cu13
cmake -S . -B build-sm86 -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=86 \
  -DCMAKE_CUDA_COMPILER=$T/bin/nvcc -DCUDAToolkit_ROOT=$T -DINGINE_BUILD_TESTS=ON
ninja -C build-sm86
ctest --test-dir build-sm86 -LE model     # kernel / unit tests
ctest --test-dir build-sm86 -L model      # full-model tests (model in ../models/Inkling-2-Mini)
```

`.cuda-toolkit/` holds the pinned CUDA 13.4.92 wheels plus the three symlinks `scripts/install.sh` makes
(`lib64 -> lib`, `libcudart.so`, `libcublasLt.so`).

## What the port changes

| sm_120a feature | sm_86 replacement | Files |
|---|---|---|
| PDL (`griddepcontrol`, programmatic launch attribute) | no-ops / attribute dropped: kernels run in stream order | `kernels/common/arch.cuh`, `common/pdl.cuh`, `core/pdl.cuh`, `dense/cluster.cuh`, `moe/moe.cu`, `attn/attn.cu` |
| `cvt.rn.f16x2.e2m1x2` (NVFP4 experts) | byte permute + masks + one exact `__hmul2` by 2^14 | `kernels/common/fp8.cuh`, `moe/moe.cu` |
| `cvt.rn.f16x2.e4m3x2` (FP8 scales, MXFP8, FP8 dense, FP8 KV) | byte permute + masks + one exact `__hmul2` by 2^8 (cuda_fp8.h's sm<89 fallback loops per byte) | `fp8.cuh`, `moe.cu`, `dense/gemv.cu`, `dense/dense.cuh`, `prefill/common.cuh`, `attn/attn.cu` |
| 16-CTA clusters + DSMEM `st.async` / mbarriers (router, message gates) | ordinary grid; exchanges through L2 + a reusable software barrier (`group_sync.cuh`); ≤ 48 CTAs, always co-resident | `kernels/common/group_sync.cuh`, `dense/router.cu`, `dense/gates.cu` |
| cluster barrier in decode attention | kernel split at the barrier: `attn_finish_kernel` merges the 16 partials and does the owner's writes (staged in the workspace). M > 1 blocks need ~96 KB shared memory, so 128 blocks cannot be co-resident on 82 SMs and a software barrier would deadlock | `attn/attn.cu` |

Decoding is exact: every finite E4M3 / E2M1 code gives the same FP16 bits as the hardware instruction
(E4M3 NaN is never stored: caches and FP8 dense weights are written saturated).

## Test results on the RTX 3090

- `ctest -LE model`: all pass. `kernels_dense`'s bit-lock hashes were recorded again for sm_86 (router
  identical to the 5090 for every M; mix at M = 5, 7, 8 and message_gates at M = 1 differ in last bits under
  sm_86 code generation, all within the reference tolerances).
- `model_parity` (`ingine-validate` vs the Python golden data, 330 stages): KL mean 2.2e-3 (limit 1e-2),
  max 5.0e-2 (limit 0.25), top-1 0.979 (limit 0.95).

- `ctest -L model`: all 11 pass (generation and speculative parity, model paths, prefill BF16 / FP8 KV,
  drafter, forced replay).
- The RTX 5090 (`-DCMAKE_CUDA_ARCHITECTURES=120a`) build still compiles; not run (no Blackwell GPU here).

`ingine-bench --long-prompt N --long-decode T` times T decode steps after an N-token prompt; numbers vary by
about +-3% between runs (the card runs at its 350 W limit). GPU memory, whole card including ~1.9 GiB for the
desktop: 21.0 GB peak at 32K context (plain), 22.2 GB with DSpark, 23.0 GB at 64K context with DSpark and a 30K
prompt; 64K is the practical limit with all experts in VRAM; 256K runs with `--offload-experts 4`.

### Measured peaks of this RTX 3090 (`mma.sync` loops, streaming reads)

| | |
|---|---:|
| BF16 x BF16 -> FP32 `mma.m16n8k16` | ~136 TFLOP/s (not half rate on this card) |
| FP16 -> FP16 / FP32 `mma.m16n8k16` | ~139 / ~141 TFLOP/s |
| INT8 `mma.m16n8k32` | ~281 TOP/s |
| DRAM read | 888 GB/s |

FP32 accumulation is full rate here, so the exact BF16 tensor-core path is also the fastest one that keeps the
model's arithmetic; INT8 would need per-weight integer scales that NVFP4's BF16-rounded decode does not have.

### sm_86 kernel work (no PDL, no clusters, no FP4 conversion instructions)

- **Prefill MoE grouped GEMM** (`kernels/prefill/moe.cu`, `wsp::gemm_kernel`): warp-specialised. 8 producer warps
  issue the gathered activation rows with `cp.async` and decode the NVFP4 / MXFP8 weights (half a row per
  thread, next stage's raw codes prefetched, E2M1 -> FP16 by byte permutes instead of a shared-memory table)
  into a 3-stage ring of BF16 tiles; 8 consumer warps only run `ldmatrix` + `mma.sync` (m-tile count as a
  template parameter: branch-free k loops). Named barriers (`bar.sync` / `bar.arrive`) hand stages over; the
  decode of round i + 2 overlaps the MMAs of round i. 62 -> 83 TFLOP/s (gate/up) and 65 -> 86 (down) on uniform
  routing; same products and K-ascending accumulation as before (bit-identical).
- **Prefill attention**: the relative-bias gathers are issued before the QK MMAs (sliding visit 0.81 -> 0.68 ms).
  Prefill chunks up to 7168 tokens (`--prefill-chunk`, 128 key tiles per call).
- **Decode moe_down** (`kernels/moe/moe.cu`, `moe_down_rows`): one block per (16-row tile, unique expert), 9 warps
  of one register-loaded step each; the expert outputs go to a device buffer and the block completing a tile
  (last arriver, deterministic) does the weighted sum and conv. The 144-block kernel fitted one block per SM
  and ran in two waves. 26 -> 21-23 us at M = 1, 41 -> 34 at M = 2, 65 -> 56 at M = 4 (bit-identical).
- **Decode attention**: the key split per KV head is decoupled from the 16 output blocks of attn_finish_kernel
  and sized to fill the 82 SMs in one wave (20 blocks per head at M = 1, 10 for M > 1: 128 one-SM blocks ran
  M > 1 in two waves). 128K context, FP8 cache: M = 1 383 -> 337 us (796 GB/s), M = 2 / 4 / 8 647 / 810 / 968
  -> 554 / 675 / 810 us; sliding M > 1 ~15% faster.
- Tried and dropped (measured slower): persistent decode MoE kernels (register or `cp.async` pipelines over
  64-byte row pieces lose DRAM locality and the L2 256-byte prefetch), shared-memory staged decode tiles,
  2-expert moe_down blocks, more steps per moe_up warp (it is issue-bound on the NVFP4 decode, ~5.7
  instructions per weight without `cvt.e2m1x2`), K steps of 32 with 2 CTAs per SM for the prefill GEMM, a
  deeper raw-FP8 tile ring for M > 1 decode attention (latency-bound per tile, not bandwidth-bound).
- Benchmarks: `INGINE_BENCH=1 build/tests/kernels/kernels_bench` (decode MoE / proj / router / attention at M = 1,
  2, 4, 8, graph-replayed; `INGINE_BENCH_ONLY=moe|proj|router|attn`), `INGINE_BENCH=1 build/tests/prefill/prefill_bench`.

Remaining ideas: M > 1 decode attention with per-warp key ranges and softmax state (no block barriers per
tile; ~1.6x at M = 2 on long contexts), the prefill relative bias computed in the attention kernel (drops the
98 MB `rel_logits` write per call and ~50 KB of chunk memory per token), 256-row MoE tiles for heavily routed
experts, folding attn_finish into the main kernel (last arriver per head).

### Where decode time goes (nsys, plain decode, per token ≈ 7.3 ms, before the sm_86 kernel work)

| kernel | ms / token | DRAM bandwidth |
|---|---:|---:|
| dense GEMV `proj` (48×) | 1.29 | ~83% |
| `moe_up` NVFP4 / MXFP8 | 1.69 | ~75% |
| `moe_down` NVFP4 / MXFP8 | 1.29 | ~50%: 144 blocks at 1 block/SM = two waves on 82 SMs (now ~1.0 ms) |
| head GEMV | 0.55 | ~95% |
| out-proj GEMV (`ConvEpi`) | 0.51 | ~75% |
| attention + `attn_finish` | 0.71 | latency-bound |
| gates, mix, router | 1.24 | latency-bound |

### Embedding table in system RAM (default on sm_86)

The BF16 `[201024, 2304]` embedding (0.86 GiB) is read from the file into pinned, device-mapped host memory;
the decode, prefill and drafter embed kernels fetch their rows over PCIe (`model/weights.cpp`,
`embed_in_host_memory()`). `INGINE_EMBED_HOST=0` puts it back in VRAM, `=1` forces it on other builds.
Same values, so parity is unchanged (KL mean 2.244e-3, top-1 0.979). Measured at 32K context, plain decode:
engine VRAM 19,094 -> 18,212 MiB (-882 MiB); decode 132.9 / 131.4 -> 131.4 / 131.1 tok/s (within noise).

### Expert offloading

`--offload-experts GIB` keeps routed experts in system RAM: CPU expert pool during decode, an adaptive VRAM
expert cache, staged prefill. 4 GiB offloaded runs upstream's 256K-context DSpark profile on the 3090.
See [EXPERT-OFFLOAD.md](EXPERT-OFFLOAD.md).

### Image input

The vision tower runs on the CPU (AVX-512 BF16 kernels, 0.6 GiB of host memory, no VRAM): image parts in chat
requests as `data:` URLs, ~70-100 ms per typical photo, ~0.7 s for a 1024-token image. See
[IMAGE-INPUT.md](IMAGE-INPUT.md).

### Startup (cold time to first token)

Measured boot-to-ready of `ingine-serve` (256K-capable profile at 64K context, DSpark), RTX 3090, Lexar NM790
(6.5 GB/s with parallel direct reads); "cold" = the checkpoint evicted from the page cache:

| | before | now |
|---|---:|---:|
| cold, all experts in VRAM | 6.5 s | 4.3-4.9 s (disk-bound) |
| warm | 2.6 s | 2.5 s |
| cold, `--offload-experts 4` | 12.7-20.8 s | 5.8-6.1 s |
| warm, `--offload-experts 4` | 13.2 s | 3.8 s |
| first request's time to first token | 132-146 ms | 74 ms (= later requests) |

What changed:
- Cold reads use O_DIRECT with many 16-32 MiB requests in flight (`core/file_read.h`, `DeviceUploader`): the drive's
  full speed instead of the page cache's readahead pace (this system's NVMe has a 16 KiB readahead window).
  Chosen per load by page-cache residency (`mincore`); `INGINE_LOAD_DIRECT=1/0` forces it.
- The offload expert store uses 4 KiB pages, faulted in on 16 threads before the reads: huge-page faults stalled
  in memory compaction (1.3-6 GB/s); the CPU expert kernels measured no TLB cost.
- After startup the server reads the checkpoint back into the page cache at idle I/O priority, so the next start
  is warm (`INGINE_REWARM=0` skips it).
- The drafter's FP64 head fold (~0.4 s per start) is cached in `~/.cache/ingine` (`INGINE_CACHE_DIR`, `-` = off).
- A 2-token warm-up generation at startup takes the first prefill's one-time setup (~60 ms) off the first request.
- `INGINE_BOOT_TRACE=1` logs every startup phase.

Not done: with offloading, short prompts still wait ~240 ms for their first token (75 ms without): their prefill
reads the cold experts they route to over PCIe (~4 GB for a 17-token prompt).

### Routing trace

`INGINE_ROUTE_TRACE=<file>` (set when the server or bench starts) appends every decode router selection to a
device log, written at shutdown (`kernels/dense/route_trace.cu`); `tools/route_offload_study.py` analyses it.
See [EXPERT-OFFLOAD.md](EXPERT-OFFLOAD.md).

## Serving

```bash
D=~/Experiments/inkling-ingine-3090
$D/native/build-sm86/apps/serve/ingine-serve --engine --model-dir $D/models/Inkling-2-Mini \
  --ablation $D/models/Inkling-2-Mini/inkling-2-mini-abliterated.safetensors \
  --host 127.0.0.1 --port 8003 --max-ctx 65536 --dense-fp8 --kv-fp8 --spec --spec-threshold 0.8 \
  --model-id inkling-2-mini-abliterated
```

`setup.sh` / `scripts/install.sh` are unchanged and still refuse non-sm_120 GPUs and build `120a`.
